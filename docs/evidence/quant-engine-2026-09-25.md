# 백테스트 엔진 교체(quantlab) 검증 — 2026-09-25

- 대상 브랜치: `claude/wonderful-faraday-826uz8`(Phase 2 위에 쌓음)
- 포트폴리오 계획 Phase 3이다. 계산 규칙은 [방법론 문서](../methodology/backtest.md)에 있다.

## 문제

기존 `POST /api/quant/backtests`(`python-stock-backend/quant.py`, 교체 전 커밋 `0102cf9`)에는 계산 오류가 7개 있었다.

| # | 오류 | 위치(교체 전) | 결과 |
|---|---|---|---|
| 1 | `fast`/`slow`를 파싱만 하고 쓰지 않음 | `:245` | 어떤 값을 넣어도 MA 20/50 결과 |
| 2 | 신호를 낸 봉의 종가로 체결 | `:265-268` | 신호에 쓴 가격으로 거래(미래 참조) |
| 3 | 거래별 수익률 × √252로 Sharpe 계산 | `:293-300` | 연 18회 거래에 매일 거래한 것처럼 연환산, Sharpe 587 같은 값 |
| 4 | 청산 시점 자산으로만 MDD 계산 | `:296` | 보유 중 낙폭이 빠져 MDD 0% |
| 5 | 첫·마지막 신호 사이 날짜로 CAGR 계산 | `:281,305` | 기간이 신호에 따라 달라짐 |
| 6 | 이동평균·RSI를 부분 창으로 계산 | `:123-134` | 3일째 "50일 이평"이 3일 평균 |
| 7 | 입력 파싱이 `try` 밖 | `:244-251` | `"fast": "x"` 같은 입력에 500 |

그 밖에 다음 문제도 있었다.
- 마지막 날 강제 청산(`:165`)
- GET 요청(`/factor-analysis`) 안에서 DDL 실행(`:346`)
- 기간 조건 없는 전체 조회(파티션 제외가 동작하지 않음)

## 바꾼 것

**엔진(`src/quantlab`, Flask·DB 의존 없음)**
- `indicators`: 창이 다 차야 값이 있음. 돌파 기준은 오늘 봉을 제외
- `strategies`: 기존 6개 전략 이관, fast/slow 실제 사용, 범위 검증
- `engine`: 종가 신호 → 다음 봉 시가 체결, 수수료·슬리피지·매도세(bp), 전액 매수(KRX 정수 주, 코인 소수 8자리), 봉마다 평가
- `metrics`: 일별 자산곡선 기반 Sharpe·Sortino·MDD·CAGR(KRX 252, 코인 365)·Calmar·노출도·회전율
- `backtest`: 결과 + 같은 비용의 매수 후 보유 + 계산 영수증
- `receipts`: 입력 봉 sha256·파라미터·엔진 버전으로 영수증 ID를 만들고, git 커밋을 기록
- `validation`: 워크포워드
- `research`: 표본 내 vs 워크포워드 리포트 CLI

**API(`quant.py`)**
- 입력 검증을 `try` 안으로 옮김(잘못된 값은 400, 없는 종목은 404)
- `marketdata.store.load_bars`로 기간을 지정해 조회(기본 최근 3년, 최대 20년)
- `backtest_runs`에 영수증 단위로 저장. 같은 입력이면 새로 저장하지 않고 기존 실행을 200으로 반환, 새 실행은 201
- 기존 `strategies`·`trade_logs`·`performance_metrics`에도 계속 기록
- 응답
  - 화면이 읽던 키는 유지(퍼센트 단위)
  - 추가: `receiptId`, `receipt`, `reused`, `strategy`, `parameters`, `metrics`, `benchmark`, `equity`(일별 자산·보유·낙폭), `trades`, `source`
- `/results`에 `strategyId` 필터 추가
- `/factor-analysis`의 GET 안 DDL 제거(스키마·샘플은 `database/quant-postgres.sql`이 만든다)

**스키마**
- `backtest_runs` 추가, `trade_logs.quantity`를 `numeric(24,8)`로 변경(코인 소수 수량)
- 새 DB는 `database/quant-postgres.sql`이 만든다.
- 기존 DB는 `flask --app app init-quant-db`(`marketdata.store.ensure_schema`, 멱등)로 올린다. Compose의 `init` 서비스가 이 명령을 실행한다.

**화면(`quant.html`)**
- 자산곡선(전략·매수 후 보유)·낙폭 차트: lightweight-charts 4.2.0
  - Apache-2.0, npm 레지스트리 메타데이터로 확인
  - unpkg 파일이 npm tarball의 파일과 바이트 단위로 같음을 `cmp`로 확인하고 SRI(sha384)를 붙임
- 전략·매수 후 보유 지표표, 계산 영수증 펼침
- 전략 버튼은 각 전략의 기본 기간을 쓴다. 이전 화면은 모든 전략에 20/50을 보냈는데, fast/slow가 실제로 쓰이게 되면서 이대로 두면 "단기 추세추종 5/20"이 MA 20/50으로 바뀌었을 것이다.

**이미지**: `GIT_SHA` 빌드 인자로 영수증에 커밋을 남긴다(이미지에는 `.git`이 없다).

**구현 중 찾아 고친 것**
- 워크포워드가 초기자본 1.0으로 돌아 KRX 정수 주 매수가 불가능했다. 모든 구간이 현금이었다.
- 검증 구간이 학습 구간 마지막 목표 포지션을 넘겨받지 못했다.
- 화면 요율 0.00015를 bp로 바꾸면 1.4999999999999998이 되어 영수증 ID가 흔들렸다.
- 표준편차가 사실상 0인 수익률에서 Sharpe가 임의의 값이 되었다. 이제는 정의하지 않음(null)으로 둔다.

**차이의 원인**
- **Sharpe**: 구 엔진은 거래별 수익률을 매일 수익률처럼 √252로 키웠다(587·388 같은 값). 새 엔진은 일별 자산곡선으로 계산한다.
  - 새 값도 4~9로 높다. SQL 샘플 가격이 사인파(`quant-postgres.sql`)라 변동성이 작고 규칙적이기 때문이다. 엔진 문제가 아니라 샘플 데이터의 성질이다.
  - 결정적 GBM 합성 데이터에서는 [리서치 리포트](../research/README.md)처럼 0.2~0.4 수준이다.
- **MDD**: 구 엔진은 청산 시점만 봐서 0%가 많았다. 새 엔진은 보유 중 낙폭을 포함한다.
- **수익률·체결 수**
  - 새 엔진은 다음 봉 시가로 체결하고 슬리피지를 매 체결에 반영한다.
  - 마지막 날 강제 청산을 하지 않는다. 보유 중이면 체결 수가 1 적고 평가액으로 남는다.
  - 창이 다 찰 때까지 신호가 없다.
- **추세추종(trend)**: 구 엔진은 5/20 규칙을 쓰면서 화면에는 20/50 파라미터를 기록했다. 새 엔진은 5/20으로 실행하고 영수증에 5/20을 남긴다.

## 달라진 동작

- 같은 요청을 반복하면 새 전략 행을 만들지 않고 기존 실행을 200으로 돌려준다. 이전에는 매번 201과 새 행이었다.
- 기본 조회 기간은 최근 3년이다(`start`, `end`로 변경).
- `quantity`는 더 이상 쓰지 않는다. 초기자본 전액 매수이고, `initialCapital`로 조정한다.
- `/factor-analysis`는 테이블을 만들지 않는다. `database/quant-postgres.sql`을 적용하지 않은 DB에서는 503이다.

## 검증하지 못한 것

- 실데이터 성과. 약관이 확인된 실데이터가 없어 합성 데이터로만 검증했다.
- 매도세·거래소 수수료의 실제 요율. 공식 출처를 확인하지 않아 기본값 0(매도세)과 가정값을 쓴다.
- 지표의 외부 라이브러리 교차검증. empyrical-reloaded가 peewee 4.5.1과 충돌해 설치하지 않았다. 대신 별도 numpy 공식과 비교했다.
- 팩터 분석(`/factor-analysis`)의 수기 OLS와 사인파 팩터 교체. 계획상 could 항목이라 이번에 하지 않았다.
- CI에서 실행한 결과. 이 문서는 로컬 실행 결과다. PR의 CI 결과는 PR에서 확인한다.
